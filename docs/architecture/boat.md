# Boat environments in T3 Code

## Data shapes

One Boat sandbox hosts one ordinary T3 environment. It can hold several projects and threads. The T3 server that creates it is its **controller** and keeps the lifecycle record in its own SQLite database. The guest owns the working directories, provider sessions, threads, and environment identity.

| Shape                | Fields and authority                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Environment          | Existing guest-generated `EnvironmentId`, descriptor, capabilities, per-device routes and credentials. A managed row references this ID once known. Local and manually paired environments work without a managed row.                                                                                                                                                                                   |
| Environment provider | A server-side driver selected by kind, initially `boat`. It can allocate, inspect and find owned resources, run fixed bootstrap operations, expose an HTTPS origin, stop, resume, delete and observe completion. Usage is a separate optional read. Driver requests carry a resolved account and immutable resource or operation identity. The controller owns business state and policy.                |
| Boat account binding | Controller-local config ID, Boat account ID, explicitly resolved wallet (personal or organization ID), and a reference to a scoped credential. Publish label, masked configured status and capabilities to authorized clients. Record each sandbox's binding at create so a change of default account cannot redirect cleanup.                                                                           |
| Boat server record   | Managed ID, controller environment ID, account binding, display name, Boat sandbox ID when known, machine size, requested TTL, pinned release, safe HTTPS origin and guest environment ID when verified. Mutable fields include lifecycle, desired power, provider observation and timestamp, first start and latest stop times, provider auto-stop deadline, retention status, and latest usage sample. |
| Lifecycle operation  | Managed ID, operation kind and request ID, immutable create payload or target ID, generation, stage, provider operation ID if returned, retry deadline and next attempt, sanitized failure code. Keep the create receipt and deletion tombstone even after the UI row is removed.                                                                                                                        |
| Usage sample         | Reported machine usage and list-price USD, reporting window and observation time. Keep current rate estimate with its source and as-of date. Expose freshness, observed power, and cleanup or purge status separately from app connectivity.                                                                                                                                                             |

Use a unique controller/request pair for create and a unique account/wallet/sandbox ID for adoption. Count unresolved creates and pending stops against any active-machine limit until provider state settles. A repeated mutation request returns the existing operation. An identical key with different inputs is a conflict. The guest environment ID is never derived from the Boat ID, name, or hostname.

### Lifecycle

| State        | Meaning and transitions                                                                                                                                                                                                                                                                |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provisioning | Create or Resume accepted. Allocate or wake the same sandbox, install or verify T3, and prove the guest descriptor and compatible endpoint. Then enter Running. Cancel records a desired stop and completes discovery before issuing it. Errors enter Failed or trigger cleanup.       |
| Running      | The latest Boat observation indicated live compute and T3 startup was verified. A device may still need to pair or reconnect. Stop enters Stopping. External archive or deletion updates the row after confirmation. A broken socket alone changes connection health.                  |
| Stopping     | Stop was requested or Boat reports archival in progress. Retain the row and its routes. Wait for provider completion. An external resume that supersedes a stop is surfaced as a conflict with fresh power state.                                                                      |
| Stopped      | Boat confirmed archival. Compute has stopped. Keep the guest ID and device credentials for reconnect. Snapshot may be available or expired. Resume returns to Provisioning if the disk is available.                                                                                   |
| Failed       | A create, bootstrap, or lifecycle action needs attention. Show the failed step and independently show last observed provider power, its age, and whether cleanup is pending. Retry continues the same operation when safe. Stop and Delete remain available for known owned resources. |

Delete is a separate, explicitly confirmed action available for a known stopped sandbox in the initial release. The row shows deletion pending until confirmed and then yields to a tombstone. A provider 404 after an accepted purge can confirm unavailability, while purge completion requires the deletion-operation status. External deletion and snapshot expiration disable Resume. Disconnecting, removing a connection, closing the app, and losing the controller each have their own semantics and never imply a provider stop.

## Existing T3 boundaries

- The environment is a running server under an OS user. Its persisted identity survives restarts and address changes. Local desktop starts its own server. An SSH environment already has a machine and uses the SSH launcher to bootstrap a pinned T3 runtime, open a loopback forward and pair. T3 Connect adds discovery and a tunnel to a linked server. These paths establish reachability and sessions. They leave VM allocation and billing to the owner. [Remote access](../user/remote-access.md), [SSH launcher](../../packages/ssh/src/tunnel.ts), [environment identity](../../apps/server/src/environment/ServerEnvironment.ts), [T3 Connect](../internals/06_t3-connect.md)
- Web, Electron and mobile reach environments through the shared connection catalog, authorization store and supervisor. Pairing checks the descriptor before exchanging the one-time credential and persists a device session. Hosted web speaks directly to the environment. Work remains environment-scoped, including filesystem paths, provider auth, checkpoints and transcript state. A client can lose its route while the guest continues running. [Connection runtime](../internals/09_connection-runtime.md), [pairing onboarding](../../packages/client-runtime/src/connection/onboarding.ts), [environment auth](../internals/04_environment-auth.md)
- Put lifecycle in one Effect service and durable worker under `apps/server`. Keep the Boat REST adapter behind that service. Use the existing SQLite migration path and a narrow status subscription or snapshot keyed by managed ID. The Boat adapter owns schema decoding, allowlisted requests, provider state mapping, and safe error categories. Guest installation and pairing live in a bootstrap module with access only to fixed operations on owned resources. [Server Effect conventions](../internals/02_effect-services.md), [SQLite persistence](../../apps/server/src/persistence)
- Define wire shapes and capability advertisement in `packages/contracts`. Use thin scoped RPC handlers, guarded client commands and shared client-runtime state. Restrict account setup, pairing mint, spending and teardown to explicitly authorized controller owners. Keep generic remote and agent sessions out of these permissions by default. Lifecycle service operations are reusable by policy-gated MCP or schedules. Initial spending and deletion actions require a human, with periodic reconciliation owned by the service. [RPC authorization](../../apps/server/src/auth/RpcAuthorization.ts), [client permission gates](../../packages/contracts/src/clientRpcPermissions.ts)

## Boat API and credential boundaries

Use Boat REST v1 from the controller. The `boat` executable was absent on this machine's PATH, so CLI behavior was researched from its published reference. For operator diagnostics the corresponding commands are `boat new`, `boat info`, `boat exec`, `boat host`, `boat stop`, `boat resume`, `boat usage` and `boat delete`. REST supplies a documented create idempotency contract, labels, an explicit wallet, operation IDs and machine-usage observations. The controller needs no installed CLI or CLI login. [API overview](https://docs.boat.dev/api/v1), [CLI reference](https://docs.boat.dev/cli-reference)

- The user creates a dedicated scoped key in Boat and enters it through an owner-only secret write on the chosen controller over a trusted local or TLS connection. Resolve it on the controller through the existing secret-store path or its secret-provider reference mechanism. Prefer a write-only form with a configured/invalid status and explicit rotation. Keep raw keys out of settings JSON, process-wide environment variables inherited by tools, SQLite, app state persistence, URLs, shell arguments and guest data. Use a server-side redacted value for the HTTPS authorization header to the fixed Boat API. Apply the narrow actions needed for create, inspect, exec, host, stop, resume and delete-own. Prove that account lookup, ownership-scoped list, usage and purge status work for this key. Require the same account and wallet on rotation and retain the old binding until the replacement can inspect and clean up existing resources. A different key's delete-own grant may leave older sandboxes outside its authority. Prove Boat rotation preserves access before retiring the old key, or finish cleanup through Boat with the original authority. [Boat key scopes](https://docs.boat.dev/api-keys/scopes), [current Boat account](https://docs.boat.dev/api/reference/account/get-current-boat-user), [T3 secret store](../../apps/server/src/auth/ServerSecretStore.ts), [T3 server settings](../../apps/server/src/serverSettings.ts)
- Create with explicit private visibility, `noEnv: true`, snapshots enabled, and finite `ttlSeconds`. Pass no account environment or per-sandbox secret bundle. The initial release requires a wallet with restorable snapshots. Read its retention policy if authorized, or collect explicit confirmation from the wallet owner when the scoped key cannot read it. Reject known zero-retention wallets and surface any policy changes before claiming a stop preserves data. Boat still gives the guest its own port-hosting capability. Treat the sandbox and its coding agents as a separate OS trust boundary. A developer signs in to the agent CLI and repository from the guest through the normal provider/source-control paths with explicitly scoped credentials where available. The initial smoke test uses a public repo and the Replay ACP fixture. Bundled T3 does not auto-register Replay (dev), so configure the existing replay script and scenario as a local ACP provider in the disposable guest only. Test one real guest-authorized harness before release. This feature inherits each guest's advertised T3 provider support. [Create sandbox](https://docs.boat.dev/api/reference/sandboxes/create-sandbox), [Boat key scopes](https://docs.boat.dev/api-keys/scopes), [T3 security model](../../SECURITY.md), [Replay fixture](../../apps/server/src/provider/ProviderInstanceRegistryHydration.ts)
- Allow telemetry fields by name. Exclude HTTP request headers and raw provider bodies, command stdout and stderr, session tokens, pairing links, exec history and secret-bearing errors from application logs, traces, crash reports and job records. Boat itself retains command text and output. Treat its command channel as visible to the Boat account and suppress plaintext pairing output there too. [Boat command history](https://docs.boat.dev/long-running-tasks/command-history)

## Bootstrap and pairing

1. Commit a pending record and start the Boat create with ownership labels. Wait for Boat to accept commands. On a clean VM, use a fixed bootstrap entry point, an exact trusted Linux T3 artifact and its verified checksum. Reuse the release selection and verification conventions already used by the installer and SSH launcher. Select an upstream artifact only after proving wire compatibility. If fork-only changes are required, publish a pinned fork build through the equivalent trusted release pipeline. Bootstrap commands contain fixed configuration and validated identifiers. Avoid using names, repository URLs or message text as shell source. [CLI installer](../../scripts/install.sh), [release metadata](../../packages/shared/src/cliRelease.ts), [SSH launcher](../../packages/ssh/src/tunnel.ts)
2. Run T3 as a dedicated unprivileged guest user with one stable base directory on the snapshotted disk. Supervise the process through a boot-enabled service with a fixed loopback port, no interactive login or launch URL, and a bounded startup check. Start with the existing Linux T3 service and confirm systemd user lingering on Boat. If that manager is unavailable, prove equivalent boot supervision with a service unit that runs as the guest user. Install atomically and serialize bootstrap by guest lock so repeats repair the same install and start at most one server. Record the ID from an in-guest descriptor; do not rely on the eventual public response as the first source of identity. On Resume verify the existing base directory and guest ID before reopening the route or allowing pairing. Boat may reuse a warm process or boot on a new address with only disk state. [T3 background service](../user/background-service.md), [Boat snapshot contents](https://docs.boat.dev/snapshots/whats-saved)
3. Expose only the T3 port via Boat HTTPS hosting with the localhost relay and public mode. The resulting origin has no Boat token and uses T3's ordinary scoped auth as its public access boundary. Boat terminates TLS and is part of the transport trust boundary. The default Boat protected URL sets a third-party cookie and cannot be assumed to work for cross-origin browser HTTP and WebSockets. Accept only the expected Boat HTTPS origin, exact port configuration and credential-free URL shape. Fetch the descriptor without following redirects, verify identity and protocol from the controller, and repeat the identity check from the actual client before any credential exchange. Prove preflight, auth, WebSocket tickets/upgrade and reconnect from hosted web and mobile. Verify that the proxy forwards Authorization and DPoP and that T3 sees the external host and HTTPS scheme through Host and X-Forwarded-Proto. A successful bearer request alone is insufficient proof that proof-bound sessions work. If public ingress is unacceptable or fails that gate, make T3 Connect or a private route the prerequisite and prove its headless linking and lifecycle before shipping. [Boat hosting](https://docs.boat.dev/hosting), [loopback and WebSocket routing](https://docs.boat.dev/hosting/how-it-works), [T3 transport trust](../internals/05_remote.md), [T3 request reconstruction](../../apps/server/src/requestUrl.ts)
4. Pair on demand for each authorized device, automatically for the initiating device while it remains present. The controller asks the guest to mint a short-lived ordinary one-time credential with `t3 auth pairing create` for its persisted base directory. The guest consumes CLI stdout locally and seals the credential to an ephemeral controller public key using a standard hybrid public-key encryption envelope. Emit only ciphertext and a safe outcome code through Boat; suppress shell tracing, raw stderr and plaintext temporary output. Deliver the result only to the requesting owner session via a private, non-cacheable response with RPC payload observability disabled. The client calls normal onboarding with the independently verified expected guest ID, redeems directly with the guest, and stores only its T3 session in the normal credential store. Never place the pairing payload in a status stream. If the browser closes or redemption fails, allow the credential to expire or revoke it and mint anew. No durable operation depends on the initiating device staying connected. [Pairing CLI](../../apps/server/src/cli/auth.ts), [client onboarding](../../packages/client-runtime/src/connection/onboarding.ts)
5. Bring up projects, clone or open a repository on the guest and start threads via the ordinary environment picker. An already paired device can keep working directly while the controller is unavailable. A newly paired device first needs a reachable authorized controller or an existing guest pairing flow. Connecting the controller via LAN, SSH, or T3 Connect does not change the guest's direct route. No app-hosted provisioning service is needed. [Remote architecture](../internals/05_remote.md)

## Retry, teardown and reconciliation

- **Create once.** Persist request ID, immutable normalized payload, first dispatch time and labels for role, controller identity and managed ID before the network call. Use that UUID as Boat's `Idempotency-Key`. Within Boat's 24-hour retention window, retry ambiguous failures with the exact same account, key and body. Back off on in-progress conflicts or rate limits. Once the window elapses, perform fully paginated label discovery in the pinned wallet. One matching owned sandbox can be adopted; zero matches or multiple matches leave an explicit unresolved record. Never replay an expired create key as if it still fences allocation. Persist the returned sandbox ID before side effects beyond create. [Create contract](https://docs.boat.dev/api/reference/sandboxes/create-sandbox), [list filters and pagination](https://docs.boat.dev/api/reference/sandboxes/list-sandboxes)
- **Fence workers.** Serialize lifecycle for each record, use durable claims and generation checks for stale writes and re-inspect after ambiguous non-create operations. A stop during create is durable intent. Finish discovery, then stop the found machine before exposing or pairing it. Keep a pending record until any in-flight create is resolved, including results arriving after cancellation or controller restart. Never retry an exec blindly after losing the reply. Inspect the install marker/service first, then safely reapply idempotent bootstrap. A bounded TTL covers the time when the controller is down.
- **Stop and resume.** Warn when active work may be interrupted. When the guest is reachable, attempt bounded graceful shutdown through the in-guest service manager before requesting Boat's graceful stop. Use the guest's usual shutdown and recovery semantics. Keep Stop usable when the guest is unreachable. Boat stop coalesces repeated requests and reports a stop operation. Confirm archival before showing Stopped, and show a provider-reported snapshot failure as still stopping with the last observed power state. Leave forced stop to explicit/manual provider intervention because it can discard disk changes. Resume targets the same sandbox ID and a finite fresh TTL. After a lost response, inspect the same resource and retry only when its observed state and operation history permit it. Confirm the same T3 identity, compatible descriptor and route again. Persisted threads and files return. Active processes or turns can be interrupted and may need the existing T3 recovery path. [Boat stop operation](https://docs.boat.dev/api/reference/sandboxes/stop-and-archive-sandbox), [resume](https://docs.boat.dev/api/reference/sandboxes/resume-sandbox)
- **Delete once.** Show a separate purge confirmation naming the stopped target and the workspace and thread data at risk. Point users to existing migration or handoff before stopping if they need to retain work elsewhere. Persist intent and use Boat's required `X-Ascii-Confirm-Delete` header with the stored sandbox ID. Record the returned operation ID and poll to completion. If the reply is lost, retry only against that ID and binding. A 404 on a formerly visible sandbox with verified account/access and a complete inventory establishes absence, with purge status unknown if no operation receipt can be recovered. An auth failure or partial list cannot establish absence. Once unavailable, let each client remove its guest route and credentials, and retain provider cleanup evidence in the controller tombstone. Saved snapshots and forks have independent lifetimes. [Delete sandbox](https://docs.boat.dev/api/reference/sandboxes/permanently-delete-sandbox-data), [deletion status](https://docs.boat.dev/api/reference/account/get-deletion-operation), [thread migration](../user/thread-migration.md), [portable handoffs](../user/portable-handoffs.md)
- **Reconcile and recover.** On startup and a bounded, jittered schedule, inspect active/pending records and sweep labeled inventory. Automatically request graceful stop for resources tied to failed or cancelled operations with proven ownership. Keep the stopped disk for manual recovery or explicit deletion. Show label matches with no durable owner record as possible orphans. Require an authorized human to inspect and adopt or clean them up. Never touch unlabeled, foreign, or ambiguously owned machines. Keep credentials and ownership bindings for outstanding cleanup or show how to finish it in the Boat dashboard. Provider TTL is the backstop if the controller or its credentials are gone. An external restart is surfaced with its new deadline, without silently removing it or starting another VM. [Provider auto-stop](https://docs.boat.dev/long-running-tasks/auto-stop)

## UI, cost and rollout

**Settings → Environments → Add environment → Boat** is the create path. Select an authorized controller if more than one is available, then name and size. Show the finite stop deadline, hourly list rate, and that stop interrupts work. Default proposal is Small with a one-hour wall-clock TTL. It is a deadline from create or resume. T3 runs its own harnesses and does not use Boat integrated prompts to extend it. A managed row shows state and stage, connection health, last provider observation, uptime or machine usage, cost estimate, deadline, and Stop, Resume or Delete as applicable. Show a retention warning for stopped disks (Boat documents at least 14 days for standard retention, with different behavior under zero retention) and use provider expiry data to disable Resume. Provide a Boat dashboard fallback when the controller is offline. [Auto-stop](https://docs.boat.dev/long-running-tasks/auto-stop), [pricing](https://docs.boat.dev/pricing), [retention](https://docs.boat.dev/data-retention)

Once paired, the guest appears in the normal project and chat environment selectors. Display a lifecycle affordance that opens the managed row, including from mobile settings and ordinary settings navigation or search. Existing command-palette/new-thread and keybinding choices use the paired guest as an ordinary environment. Keep the first create affordance in Environment settings. Web and desktop share the existing React surface, including hosted and self-hosted web. Mobile uses its native Settings → Environments screen and the same controller capability. Verify local controller and remote controller routes, a second device, and translate client copy. [Web Add environment](../../apps/web/src/components/settings/AddEnvironmentDialog.tsx), [mobile Environments](../../apps/mobile/src/features/settings/SettingsEnvironmentsRouteScreen.tsx), [translations](../internals/14_i18n.md)

Use provider-reported list-price usage when available, cached and refreshed in batches or on demand for detail. Boat usage seconds are size-weighted. Use provider start and stop timestamps for elapsed wall time. Keep estimate and timestamp visible when stale. The documented Small and Default rates at research time were $0.018 and $0.036 per hour, billed per second. A confirmed archival means machine-time charges have ended. Subscription minimums, start overages, saved snapshots and any agent/model usage are separate. Display the sample as machine usage with the reporting window. Link to Boat for wallet charges and invoices. [Boat usage endpoint](https://docs.boat.dev/api/reference/sandboxes/get-sandbox-usage), [pricing and start limits](https://docs.boat.dev/pricing)

Key release risks are relying on a public proxy without proving auth and reconnect, stale state that looks like a billing confirmation, a key that cannot clean up after rotation, unusable private repo or agent auth, interrupted work at the TTL, and provider retention or plan changes. Scope the first release to user-owned accounts and one controller per managed record. Budget enforcement, account sharing, automatic start on thread send, migration of existing threads, and reusable images can be evaluated after the basic lifecycle is proved.

## Build stages and acceptance

Use a dedicated Boat test account or wallet, a scoped key delivered through the secret path and task-owned labels. Record redacted IDs, state transitions, timestamps and outcome evidence. Every stage using a real VM ends by observing provider archival, and the disposable fixtures are explicitly purged with confirmation. A test fixture or simulated failure can complement a live test, while proof of provider behavior comes from a real VM.

| Stage                       | Work and real acceptance                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0. Transport and boot spike | On a disposable Boat, install the pinned artifact and use the published API or CLI, checking command help if installed. Verify the guest ID through exec, then pair from hosted web using proof-bound auth. Exercise authorization, CORS, ticketed WebSocket, idle reconnect and renewal. Stop, move past the warm-resume window, resume from Boat while the controller is offline and verify the boot service restores the same T3 ID and HTTPS route. Stop and purge. Resolve any proxy or service gap before building the UI. |
| 1. Provider contract        | With the intended scoped key, create a real Small VM with a finite short TTL and ownership labels. Send the same create twice and verify one Boat ID and one inventory match. Inspect usage with that key, stop it, verify archival and no increasing machine time, then purge and verify deletion completion. Verify the same key has no account-admin power and cannot operate on an unrelated fixture.                                                                                                                        |
| 2. Bootstrap and pairing    | Fresh stock Boat VM, pinned artifact, stable service and credential-free HTTPS origin. On a real browser from a different origin, verify expected descriptor, auth denial before pairing, one-time redemption, authenticated WebSocket RPC, and a thread with Replay plus a sentinel file created by a guest terminal. Inspect Boat command history and T3 logs/traces using canary credentials to prove sensitive values stayed out. Stop and purge.                                                                            |
| 3. Recovery                 | On dedicated live sandboxes, discard the successful create response and restart the controller. Verify one machine, adoption and cleanup after stop during provisioning. Simulate the elapsed idempotency window locally against labeled live inventory and verify recovery issues no create. Repeat after a bootstrap failure and after a lost stop/delete response. With the controller offline, observe Boat TTL archival and reconcile on restart. Prove unrelated resources survive.                                        |
| 4. Persistence and clients  | From Settings create a Boat and start a guest-authorized real thread on a public test repo. Stop from the app and let the warm-resume window elapse, then resume and verify the same sandbox ID, environment ID, transcript, checkout and sentinel. Verify hosted web, self-hosted web, desktop and native mobile. Pair a second device and exercise management through a remote controller. Check UI state, estimates and deadlines against Boat. Delete from Settings and verify the task-owned resource is purged.            |

## Precedents

- OmarAlex24's T3 fork splits provider operations, lifecycle, pairing and client registration. It labels resources, uses an idempotency key, protects pairing output from provider command history, and leaves untracked label matches for review. Borrow those boundaries and safeguards. This design allocates an environment explicitly and lets projects and threads reuse it. [Fork design and code](https://github.com/OmarAlex24/t3code/blob/f65ffa797e859a2b6eeeaed396d625ed5aa1271c/docs/internals/sandbox-environments.md), [pairing envelope](https://github.com/OmarAlex24/t3code/blob/f65ffa797e859a2b6eeeaed396d625ed5aa1271c/apps/server/src/sandbox/sandboxPairing.ts), [T3 discussion](https://github.com/pingdotgg/t3code/discussions/27949)
- Digitalxero's plugin gives the controller durable responsibility, connects clients directly to guests, uses a provider deadline and includes a real Boat smoke driver. The plugin relies on a special host branch and prebuilt guest images. Keep these as reference for controls and proof, and use the fork's own server capability and cold bootstrap. [Plugin design](https://github.com/digitalxero/t3-sandboxes/blob/f1f850ad33bd085e6f02135b0d01b27b4cb82063/README.md), [Boat smoke script](https://github.com/digitalxero/t3-sandboxes/blob/f1f850ad33bd085e6f02135b0d01b27b4cb82063/scripts/smoke-boat.mjs)
- Open-Inspect's Boat integration pins images, explicitly requests private VMs for org wallets, and persists runtime state under a snapshot-backed path. Codespaces shows why Stop, resume and destructive Delete should be separate from disconnecting. [Open-Inspect Boat provider](https://github.com/open-inspect/background-agents/blob/main/docs/BOAT_SANDBOX_PROVIDER.md), [Codespaces lifecycle](https://docs.github.com/en/codespaces/about-codespaces/understanding-the-codespace-lifecycle)

## Design reconciliation

Claude Opus 5.5 (high) and Codex independently converged on a server-owned lifecycle, direct client-to-guest traffic, pinned bootstrap, and finite provider auto-stop. Claude found the Expo cloud-device ledger and its uncertain-create accounting, and identified proxy request reconstruction and cold boot as release gates. The merged plan carries those into the durable worker and Stage 0. Codex's source pass contributed the T3 sandbox fork and plugin comparisons, including encrypted pairing output, and the split between provider power, client connection state and purge completion. [Expo device lifecycle](../../apps/server/src/device/EasDeviceHost.ts), [DPoP URL validation](../../apps/server/src/auth/dpop.ts)

Claude proposed a full-access peer link to reuse client pairing and cross-environment agent delegation. The link also gives the controller persistent shell-equivalent access and pulls in the linked-environments beta. Ordinary per-device onboarding covers this release's thread flow. Keep peer links opt-in when a user needs agent delegation. Claude's proposal to let short-lived pairing codes pass through Boat command output was revisited against Boat's documented output retention. The first release seals them before they leave the guest process. Keep the provider interface internal and limited to Boat's operations, with additional drivers deferred. [Peer links](../internals/05_remote.md#peer-links), [Boat command history](https://docs.boat.dev/long-running-tasks/command-history)

Claude's active-turn TTL extension would make interruption less likely while the controller is online and extends spending as a side effect of work. The first release uses a displayed deadline with no automatic extension. The same ownership rule applies to Claude's automatic orphan stop and oldest-match adoption proposals. One exact match to durable intent can be adopted or stopped automatically. Label-only and multiple matches call for human review because they may be running work and the controller cannot prove which guest belongs to the record.
