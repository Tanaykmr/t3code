# Bots in T3 Code

## Data shapes

| Shape                 | Fields and invariants                                                                                                                                                                                                                                                                                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bot**               | Stable `BotId`, owning `EnvironmentId`, display name, persona text and revision, coding `ProjectId`, DM `ThreadId`, and archive timestamp. One bot owns one DM thread. Model selection, options, and runtime mode come from that thread via the existing contract. A name change keeps the same IDs.                                                                             |
| **BotMessage**        | Read model for a human/bot message in the DM. References `BotId` and the existing `MessageId` and carries author, timestamp, and text from the thread projection. Task progress cards reference a work link. Assistant replies stream through the existing transcript.                                                                                                           |
| **BotChannel**        | One direct channel per unordered pair of distinct bot IDs in the same environment. Derive the channel key from the pair. No channel table is needed for v1.                                                                                                                                                                                                                      |
| **BotChannelMessage** | Channel key, stable ID, from/to bot IDs, originating run ID, text, timestamp, and optional reply-to ID within that channel. The server derives the sender from the active DM's MCP session. Messages are visible to the operator under the two bots' activity and can be read by either participant.                                                                             |
| **BotWorkLink**       | Read model joining `BotId`, parent DM `ThreadId`, and existing app-owned task ID to its projected child thread and latest run. Keep the child reference optional while preparing. Read status from the task and pending request projections. Use the existing environment-qualified thread link on the card and retain an unavailable state for a deleted or inaccessible child. |

Environment is part of a bot's identity from the client's perspective. The server already owns one environment database, so local rows use local IDs. V1 has a single-operator audience at that environment's operator scope. Paired devices with that grant see the same bots. A guest link or an outside MCP token does not confer access to the bot directory or peer messages.

## V1 behavior

### One DM thread per bot

Create a named bot against an existing project in the chosen environment. Both the conversation and its coding delegates use that project. The environment server stores the persona and applies it in provider turn preparation, with trusted app instructions and user-authored persona kept distinct from inbound peer text. Apply the persona on every new turn, including completion wakes and provider resumption. Codex has a turn additional-context path. Claude assembles a session prompt, so its adapter must refresh instructions on revision change or supply the revision in per-turn context while retaining chat history. Prove the policy on a resumed and compacted session. An edit applies to the next turn and does not rewrite history or restart an active run. Validate this on an adapter with explicit instruction support before broadening provider availability. The initial compatibility target is Codex and Claude plus Replay for development. Gate Cursor, Grok, OpenCode, Antigravity, Kiro, Pi, Muse Code, fx and other ACP agents out of the bot DM picker until each adapter proves persona and T3 MCP support. Coding delegates continue to use the ordinary provider catalog and its project and runtime checks.

Choose the project at creation and keep it fixed for v1. Local `delegate_task` already requires the caller and child to share a project, and its worktree path resolves the parent's commit. This also avoids treating a synthetic bot home as a code repository. Show the project next to the persona settings. Apply the existing approval-required mode where supported and reject unsupported selections or policy changes with a reason. A project and its worktree are context and isolation for files under development. OS access still follows the provider runtime mode and existing environment policy.

### Coding work and reporting

A user gives a coding task in the bot DM. The bot uses asynchronous `delegate_task` from the active DM turn, with worktree isolation for Git coding tasks. It posts a short acknowledgment with the child link and ends the turn. The same app-owned task ID powers status in the DM and the existing child navigation. The task projection and `task_status` answer progress questions. The bot yields after launching while the server watches child events. Provider-native subagents are outside this link contract. Automatic completion delivery brings the result, failure, or cancellation back into the DM after the child run, even when the client is disconnected. The bot uses that wake to post a user-facing summary of outcome, verification, remaining blockers, and the thread link. The task card stays authoritative if the summary turn fails.

An open permission or input request shows a Needs you state with a link to the actual request in the child. The user answers or stops work there. Status and badges derive from durable task and request state, so a restart or background tab does not lose them. Completion of a turn is a run outcome. The bot compares the delivered result against the requested acceptance criteria before calling the job done. For an incomplete result, allow one corrective attempt using the ordinary child continuation when available. Carry the initiating user message ID across completion wakes and enforce the allowance from the existing run/task lineage so a new wake cannot reset the budget. If a continuation cannot produce a durable result wake, report the current outcome and let the user choose the next step. Exhaustion or a human-only blocker produces a report with the next action. Use existing task cancellation and stop semantics, including suppression of late wakes for cancelled work. PR readiness can use the existing PR watch on the thread when explicitly requested.

### Peer channels

Give active bot DMs three scoped capabilities to discover eligible bots, send a bounded text message, and read their own peer messages. Support an optional reply pointer. Name the sender from stored identity and mark the body as peer-authored data. Generic agent thread-send into another bot DM must enforce the same rules so it cannot trigger a peer turn. A recipient reads peer mail through its tools on its next turn. A send updates activity and starts no model turn. This provides a two-way message history while keeping delegation as the v1 mechanism for work that must run and deliver an automatic result. Surface sender, recipient, and message timestamps to the operator. Treat inbound peer text as data. It carries neither human approval nor permission to act for the sender. Keep peer discovery and history within the owning environment even when the client is remotely connected.

## Risks and limits

| Risk                                                         | V1 decision                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A quiet or busy bot misses a result                          | Use the app-owned completion wake and durable task state. Reopening the app shows the exact child even when model summarization failed. A report lists what was verified and what remains open.                                                                                                                                                                                                                         |
| Agent loops, spend, and competing repo edits                 | Peer sends never wake a bot. Limit sends per run, peer payloads, and outstanding tasks. Start with one active coding task per bot, a small finite retry budget per user request enforced on the server, and no nested bot-managed work in v1. Use existing worktree and approval policy. The environment host must remain online for work to advance.                                                                   |
| Authority leaks through peer content or a second entry point | Bind bot tools to the active session and server-side DM mapping. Peer text and child outputs are lower-trust input. The same runtime ceiling and permission checks apply to web, remote, and MCP paths. Enforce v1 work bounds across generic launch/delegate entry points for bot-originated sessions and continuations. Human approvals stay in the linked thread.                                                    |
| Provider drift or plan mode changes behavior                 | Gate DM adapters on tested persona and MCP support. Use provider capabilities for runtime/mode combinations and project enablement. Prove behavior with Replay plus a real provider check for each enabled adapter and run model-facing evals when changing instructions/tool descriptions.                                                                                                                             |
| Reconnect and notification noise                             | Persist durable status and reports. Derive unread and Needs you from existing thread semantics. Show the child's actionable notification and use the bot's report as the normal completion notification. Avoid counting that child completion twice in a bot-aware client. Relay payloads keep the existing status format. DM report text stays in the authenticated transcript. Bound summaries and page peer history. |

## Co-architecture decision

Codex and Claude Opus 5.5 independently chose an ordinary T3 thread for the bot DM and app-owned delegation for coding work. The merged design takes Claude's on-demand bot previews, attention from existing pending requests, migration collision check, and future peer assignments in separate work threads. Codex proposed the independent bot profile, one existing coding project per bot, and passive peer channels with server-derived authorship.

| Question                                                   | Claude's proposal                                                                                                    | Decision and evidence                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Does a bot need its own project?                           | A dedicated bot project keeps persona files away from code. Older clients can browse the bot as a project.           | Give the bot a separate profile and put its DM in the selected existing project. Local `delegate_task` rejects a different target project and its worktree prep resolves the parent's commit. A bot-home project would require a new authorized cross-project launch or constrain work to the bot home. The historical fork also had to filter bot projects from ordinary project lists. |
| Is sending a peer a message the same as assigning it work? | Target a bot through `delegate_task`, start a fresh thread with its persona, and wake the requester with the result. | Ship addressed messages without a wake and reserve Claude's assignment for later. This keeps communication cheap and attributable, and preserves deliberate delegation for coding. For future peer assignments, apply Claude's ancestry and depth limits to the existing app-owned tasks.                                                                                                |
| Would a separate bot inbox simplify user feedback?         | Keep chat in the thread and derive attention. Revisit an inbox if team routing or report volume warrants it.         | Agreed. DM replies, linked child requests, and a compact activity view cover the single-operator case. ## Product decisions

- V1 ties each bot to one coding project to reuse local delegation and its result wake. If bots must serve every project from one DM at launch, the first additional design is an authorized cross-project delegate target and workspace policy, with the same app-owned task and completion delivery.
- V1 peer messages are read by the recipient during its next turn. Automatic peer conversations move up only if a single-turn, opt-in request/reply is part of the first release.
