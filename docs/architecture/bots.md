# Bots in T3 Code

## Shared data and API

Define these shapes in `packages/contracts` first. Web, Electron, and the native iPhone app use the same authenticated environment RPCs and the same thread contracts. The environment owns the data. IDs crossing environments are qualified with `EnvironmentId`.

| Shape                          | Fields and invariants                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Bot**                        | Stable `BotId`, owning environment, name, title, avatar (line glyph or authorized image asset), persona text and revision, DM `ThreadId`, optional default coding project, allowed work targets, notification preference, and archive timestamp. Model and runtime policy come from the DM thread. Rename and restore preserve IDs and links.           |
| **BotMessage**                 | Stable message reference, conversation and sender (user, bot, or system), typed content, timestamp, mention targets, optional reply-to and origin. DM text references the existing thread message. Peer and room text is stored once in its channel. Chat cards reference work, routine runs, and reports by ID.                                        |
| **BotMention**                 | A composer token with a stable target `BotId` and display label, persisted with the source message. Labels survive renames in historical messages. The server routes using validated IDs. Ordinary text that looks like a mention has no routing effect.                                                                                                |
| **BotChannel / BotRoom**       | A direct channel is keyed by the unordered pair of bot IDs. A room has a stable room ID, name, member bot IDs, default responder, and archived state. Both have ordered messages. A room participant uses its own ordinary T3 thread for execution, keyed by room and bot. The room timeline is the shared user-facing transcript.                      |
| **BotDelivery**                | Source message, target bot, causation root, initiating principal and kind, hop count, destination thread and stable dispatch ID. A unique message/recipient pair prevents duplicate wakes. Delivery can be queued, accepted, settled, blocked, or cancelled. A correlated reply has its own message ID and identifies the request it answers.           |
| **BotWorkLink**                | Bot ID, origin conversation/message, parent thread/run and app-owned task ID. Resolves to child environment, project, thread and latest relevant run. Can also point at a hosted T3 worker. The existing task projection supplies status and pending requests.                                                                                          |
| **BotRoutine / BotRoutineRun** | Bot ID, existing scheduled task ID, saved prompt, enabled flag, trigger (cron with time zone or event with source/filter), revision, and destination. Each occurrence or event ID links to the existing delivery receipt and, when dispatched, the resulting thread/run. Show the scheduler's dispatch outcome and the resulting run status separately. |
| **BotMemoryEntry / BotSkill**  | Stable ID, bot owner, revision, source, content and timestamps. Memory records scope and provenance. A skill has a name, instructions and enabled state. Both support editing and removal. The provider sees only enabled skills and a bounded set of permitted memory.                                                                                 |
| **BotReport / ReadCursor**     | Stable report ID tied to the work outcome or routine occurrence and the committed DM reply, with an optional origin-room link. Read state is a monotonic per-conversation watermark for the operator, shared across devices. Derive unread count from visible incoming messages after that watermark.                                                   |

Expose one capability-advertised Bots RPC group for directory snapshots and updates, profile and room mutations, peer/room send and history, read cursors, and the overview's work, routine, memory and skill views. Carry idempotency keys on writes. DM send, live transcript, child navigation, pending requests and cancellation keep the existing thread APIs. Extend the thread send command to carry structured mentions so desktop and the mobile outbox use the same envelope. The scheduler remains authoritative for routine definitions and execution. Unsupported hosts omit the capability and existing thread clients can still open ordinary thread links.

### Conversation delivery and access

In a DM, committing a human message with an @-chip creates a visible handoff to each explicitly addressed bot. Each recipient gets the addressed text and an origin link, with any extra source context explicitly selected for sharing. The DM's own bot runs when it is addressed or when there is no chip. In a room, one post is canonical. Explicit mentions and direct replies choose recipients. An unaddressed human post goes to the room's default responder, which can route a next step to another member. Allow explicit all-member delivery within the room's member cap. Room replies appear in the room, and room turns see only authorized room history and that bot's allowed context. A room's participant threads have independent provider contexts. Expose pending approvals only through the authenticated child thread, and keep private DMs and private memory out of room context.

Bot sends are server-attributed and wake the recipient unless the message is an explicit terminal acknowledgment. A recipient can answer asynchronously. The correlated answer appears in the exchange and can resume the requesting bot once, then closes that request. Active bots queue incoming work via normal thread scheduling. The server limits recipients per send and unique bot visits, turns and hops per root request. An agent's reply cannot create a fresh human root. Persist deliveries before dispatch and replay with stable message and command IDs. A DM's committed mention event remains replayable until its deliveries are recorded. Commit a room or peer post and its deliveries together. Project a recipient's room reply back to the room once, keyed by its committed thread message ID. Preserve thin status cards in initiating chats so operators can see queued, delivered, blocked and finished work.

Carry user, bot or routine provenance in metadata and provider context. An addressed user message can carry its explicit instruction, while a peer or webhook cannot grant additional access, supply a human approval, change runtime mode, or mint a human-origin wake. Background tasks inherit the allowed work targets and runtime ceiling of their initiating context. Block bypasses through generic thread sends and launches for bot-owned turns, including after continuation or reconnect. Guest links and outside MCP tokens have no bot directory, peer history or profile access without an explicit supported grant. Normal coding agents keep their existing thread APIs.

### Delegation across projects and hosts

Keep the DM's execution project separate from its allowed coding destinations. A bot may use a default destination, but the user can grant and revoke additional projects. Extend local `delegate_task` explicitly. Today it rejects a local project different from the parent's, resolves models in the parent workspace, and uses the parent's commit for isolated worktrees. Resolve provider enablement, cwd, repository, base ref and checkout strategy in the destination. Require worktree isolation and a destination-owned base for cross-project Git work. Reject unsupported combinations before enqueue. Use the selected repository and base from the user's request or the destination's normal default. Thread launch preparation creates the checkout and retains the existing parent/child task and result lineage. Keep parent access checks separate from target access checks.

Track work with the existing task ID and pending-request projection. Use `task_status` for a progress question and the asynchronous completion wake for ongoing work. The bot checks the requested acceptance criteria, makes one bounded corrective attempt if warranted and reports what passed, what remains and the thread link. Ask the user for human-only decisions using the existing request flow. The task card remains readable if model summarization fails. Preserve the initiating message and workload limits across follow-ups. PR readiness can use the existing PR watch when requested.

Hosted workers use an authorized linked T3 environment and `RemoteDelegation`, where the local task points to an ordinary remote thread. Show the destination before launch and retain status and cancellation semantics after reconnect. If the remote cannot confirm a stop, display that the run may still be active. This delivers optional cloud execution with the same contract and no VM provisioning dependency.

### Routines, memory and skills

Reuse Scheduled Tasks' bound-thread and webhook delivery paths. Add cron and time zone semantics to the same service. Persist the occurrence identity in UTC. Skip nonexistent local times and run once at the earlier offset for repeated local times. Retain the existing recoverable run bookkeeping. An event trigger uses a saved prompt, a source and a narrow filter. Ship signed webhooks as the event ingress, which can receive events from external services. The ingress verifies and deduplicates events before enqueue. Treat event payload as data in the saved prompt's context. A routine carries its own opt-in action scope and cannot behave as a current human approval. Keep pause, edit, manual test and history reachable from the bot overview on both clients.

Store persona, memory and skills by bot ID. Add and forget memory from chat or overview with inspectable provenance. When memory is enabled, a bot can save a lasting preference from an operator-authored DM and link to its source. Keep operator-private memory out of rooms unless the user explicitly allows it in that room. Keep memory writes scoped to the owning bot and reject imports of secrets from peer, room or webhook contexts. Use provider capability checks for persona and skills, an explicit instruction input and bounded memory selection on new turns, including continuation, routine wakes, compaction and resume. An edit applies to the next turn. Qualify Codex and Claude against those paths and use Replay in development. Gate Cursor, Grok, OpenCode, Antigravity, Kiro, Pi, Muse Code, fx and other ACP instances for bot DMs until each proves persona and MCP behavior. The coding provider catalog still follows project policy. Run the repo's model-facing evals when changing instruction and tool text.

### Notifications

Commit a report reference only when the result is visible in the DM, using a stable ID for its source outcome. Initial acknowledgments and child state changes still appear in chat or the work overview. Use one completion alert for the bot report and preserve actionable alerts for pending human requests. Derive the in-app unread count from committed chat state and suppress foreground alerts for the DM already open. On iPhone, background push requires a linked T3 Connect environment configured to publish agent activity, a registered device and OS permission. A directly paired client receives in-app state when connected and catches up on reopen. Surface notification readiness in the overview.

Extend the existing agent activity relay to recognize a committed report by ID so retries, completed child runs and later DM turns cannot send duplicate report alerts. Push contains a short status and an existing environment/thread deep link. Full report text is fetched on authenticated open. Preserve the report in the transcript if delivery fails. The mobile notification handler already routes foreground and cold-start responses and suppresses the active thread. Prefer that path over adding a second push registration.

## Verification

Run each phase against an isolated server with seeded projects, a paired iPhone and desktop/web connected to the same environment. Use Replay for deterministic outcomes. Use a real enabled provider for persona, agent-tool routing and resumption wherever Replay cannot issue the tool call. For iPhone, use the repo's `test-t3-mobile` workflow with a fingerprinted dev client, Metro, and AgentDevice. Build scenario fixtures for [the existing iOS scenario harness](../../scripts/scenarios/t3-mobile.ts). Prove notification navigation with a simulator-injected payload and prove real background delivery separately on a registered iPhone with T3 Connect and APNs. For each phase, include reconnect and a retry of the triggering command. Phase 5 also proves remote stop and link loss.

This revision was prepared on Linux without Xcode or `simctl`. T3 Device discovery reported that agent device access is off for this environment. There is no Bots implementation in this change to build or exercise. The focused check passed across seven suites and 109 tests for existing mobile navigation, push registration and notification links, shared thread commands, and server/relay alert policy. These cover the seams the plan reuses. Native layout, end-to-end Bot behavior, and real notification delivery remain acceptance gates for the implementation.

## Co-architecture record

Codex and Claude Opus 5.5 originally agreed on ordinary threads for DMs and app-owned delegates for coding. Claude proposed a dedicated project per bot, on-demand previews, child-request attention and separate work threads for peer assignments. Codex proposed an independent profile and stable authorship for peer delivery. This revision keeps the thread reuse, independent profile, on-demand overview, and existing attention logic.
